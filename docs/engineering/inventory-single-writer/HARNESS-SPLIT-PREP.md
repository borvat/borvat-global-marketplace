## أثر تغيير تاريخ الترحيلات على Supabase

1. **التتبع بالإصدار لا بالمحتوى.** Supabase CLI يسجّل الترحيلات في `supabase_migrations.schema_migrations` بالنسخة (الطابع الزمني في أول اسم الملف). تعديل محتوى ملف مطبَّق لا يعيد تشغيله، ولا يُكتشف تلقائياً. الخطر هنا ليس إعادة تنفيذ، بل **اختلاف ما يبنيه بيئة جديدة عمّا بنته بيئة قديمة**: PostgreSQL جديدة ستتلقى النسخة المقتطعة (بلا harness) وهذا هو المطلوب.
2. **`supabase db push` لا يتحقق من البصمة.** فلا يتوقف عند اختلاف المحتوى. أما الأدوات التي تحسب checksum (بعض مسارات `db diff`/CI) فقد تُظهر فرقاً يحتاج `supabase migration repair --status applied <version>` صريحاً.
3. **`supabase db reset` والبيئات الجديدة** تعيد تشغيل الملفات الحالية: بعد الفصل تصبح قابلة للبناء من الصفر، وقبل الفصل تفشل وتُسقط كائنات.
4. **الإنتاج لا يتأثر**: الملفان مطبَّقان هناك منذ تموز، وتعديل الملف لا يرسل أي SQL إلى القاعدة الحيّة. لا حاجة إلى ترحيل تعويضي.
5. **ما يجب تسجيله عند القرار:** قرار مكتوب بأن الملفين تغيّرا بعد تطبيقهما، مع SHA قبل وبعد، وتاريخ، وسبب. وأي أداة تحسب بصمة محتوى يجب تحديثها بنفس القرار.

  --reset --seed-before 20260725220916
